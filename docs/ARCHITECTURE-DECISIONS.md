# Architecture Decisions — MarsERP

This document records decisions that **override or make concrete** what `PRD.md` left open or assigned to Next.js. It exists because the PRD's original stack (Laravel 13 API + separate Next.js frontend) was superseded by an explicit choice to build **frontend and backend both in Laravel 13**.

| # | Decision | Rationale |
|---|---|---|
| 1 | **Frontend = Filament v4** (Livewire-based admin panel), not Next.js, not custom Blade/Livewire, not Inertia. | Filament ships data-dense tables, forms, filters, bulk actions, RBAC, dashboards, notifications out of the box — matching PRD §41 (UI/UX Requirements) and §57 (navigation) with far less hand-built UI code. Laravel + Filament is a single deployable app (no separate Node/Next.js runtime). |
| 2 | **Monolith, single Laravel app** (`src/`) serving both the Filament admin UI and `/api/v1/*` REST endpoints. | Matches PRD §58 "modular monolith first." REST API (PRD §33) still gets built as normal Laravel API routes/controllers for future external integration and the AI layer — Filament merely replaces the "Next.js consumes API" part with "Filament talks to the same Eloquent/service layer directly." |
| 3 | **Database = PostgreSQL 16**, single `public` schema, domain separation done **logically** (folder/module namespacing + table prefixing convention: `<domain>_<entity>`, e.g. `procurement_purchase_orders`) rather than native Postgres schemas. | PRD §39 allows "schemas or a carefully bounded table namespace." Native multi-schema Eloquent connections add material complexity (per-schema connections, migration path juggling) without MVP-stage benefit. Revisit if/when domains split into services. |
| 4 | **RBAC = spatie/laravel-permission**, wired into Filament via policies; **filament-shield** used to generate baseline resource policies. | Standard, well-audited Laravel package; satisfies PRD §7.2 Security (User/Role/Permission/Permission Group) and server-side permission checks (PRD Key Business Rule #6). |
| 5 | **Infrastructure**: Docker Compose with `app` (PHP-FPM 8.3), `nginx`, `postgres:16`, `redis:7`, `queue` (same image, `artisan queue:work`), `scheduler` (same image, `artisan schedule:work`). | Matches PRD §40 Infrastructure and §46 Reliability (queue retry, background jobs). |
| 6 | **Build order = frontend-first per module.** For each of the 8 MVP phases: migrations + models + Filament Resources (full CRUD UI, navigation, forms, tables) are built and reviewable **before** deep business-logic/service-layer work (accounting postings, approval engine execution, stock ledger automation, etc.). | Explicit instruction from product owner: review the complete UI/navigation surface first, then harden business logic phase by phase in follow-up sessions. |
| 7 | Money fields stored as `decimal(18,2)`; quantities as `decimal(18,4)`. Base currency IDR, multi-currency field present but conversion logic deferred to Finance phase hardening. | Matches PRD §11.6 tax and general finance precision needs without over-engineering MVP UI pass. |
| 8 | Manufacturing (PRD §26/§51) is explicitly **out of scope** — no tables, no menu. CRM, HR, Project Accounting (PRD §50, "Phase 2" beyond the 8 MVP phases) are **out of scope for this pass** — navigation placeholders only, no resources yet. | PRD §4 Non-Goals + PRD §49/§50 phase boundaries. Keeps this pass focused on the 8 MVP phases actually requested. |

See [MVP-IMPLEMENTATION-PLAN.md](MVP-IMPLEMENTATION-PLAN.md) for the full phase-by-phase entity/resource breakdown.
